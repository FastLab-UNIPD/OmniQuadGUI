PROJECT
-------
OmniQuadGUI: a Python 3 / GTK 3 desktop app for Ubuntu with an embedded
VTE terminal that connects over SSH to a drone's onboard computer
(Radxa Rock 5B, ROS 2, Docker). It manages containers and inspects ROS
topics. It does NOT control flight. User is a mechanical engineering
student with basic Python: code must stay simple, readable, heavily
commented, no advanced patterns. Plain-English error messages.

IMPORTANT TECHNICAL LESSONS (do not regress)
--------------------------------------------
- VTE spawn_async on this Ubuntu: parameter order is
  (pty_flags, working_dir, argv, envv, GLib.SpawnFlags.SEARCH_PATH,
   child_setup, child_setup_data, timeout, cancellable, callback)
  -> spawn works: (Vte.PtyFlags.DEFAULT, None, argv, envv, SEARCH_PATH,
     None, None, -1, None, cb). A wrong order raises TypeError that is
  INVISIBLE when launched from .desktop (hidden stderr).
- Error dialogs added in main(): any unexpected exception shows a
  Gtk.MessageDialog with traceback.
- Test pattern used all along: env -i DISPLAY=:0 HOME=... PATH=...
  python3 with monkeypatched run_ssh_background (canned answers, queue
  pop per call) and stubbed start_ssh_session; sequences tested
  SEQUENTIALLY (no interleaving); dialogs stubbed to avoid blocking.
- User's shell has ROS Jazzy sourced (LD_LIBRARY_PATH etc.) - use clean
  env for python tests; desktop app runs without it.
- My shell env shows ROS vars; that is expected here.
- Password handling: SSHPASS env var only (sshpass -e), never command
  line, never saved; sudo password via ssh stdin only. config.json
  never contains passwords.
- Default demo creds in config.json are NOT security - preview only.
